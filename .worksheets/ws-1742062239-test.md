## How the worksheet-loop extension interacts

- **Process-local guard**: `worksheetGuard.active` set in `tool_call` (pre-execution), cleared in `tool_execution_end` (post). Fast path for this session.
- **Cross-process sentinel** (✅ implemented): `.worksheets/.ws-lock` touched before writes, deleted after. Any pi process (including subagents) that loads this extension participates. Watcher checks for it before injecting.
- **Stale-lock safety**: sentinels older than 30s are cleaned up (handles crashed processes).
- **Normalized hash**: whitespace-only changes (auto-format) update the stored hash but don't inject a prompt.

## File watcher race conditions — assessment

Good research. These are real constraints of `fs.watch` / inotify / FSEvents, but their impact here is low:

- **Startup scan race**
  - **Concern:** Files created between `seedExistingHashes()` and `fs.watch()` registration could be missed.
  - **Mitigation:** `session_start` fires during pi init — no writes happen in this window because the session hasn't started processing prompts yet. Gap is nanoseconds.

- **Recursive watch gap**
  - **Concern:** `fs.watch` on a single dir doesn't see files in subdirectories.
  - **Mitigation:** Convention is flat `.worksheets/*.md`. If subdirs were used, they'd be missed — but the SKILL.md tells the agent to create files directly, not in subfolders.

- **Buffer overflow**
  - **Concern:** inotify circular buffer (16KB on Linux) drops events under high volume.
  - **Mitigation:** User is on macOS (FSEvents, much larger buffer). Even on Linux, `.worksheets/` has ≤1 event per second — orders of magnitude below overflow rates.

A periodic resync (e.g., every 5 minutes, re-read all `.worksheets/*.md` and update hashes) would eliminate the last 0.1% edge case, but adds complexity. Not worth it unless symptoms appear.
